# Independent verification — version 1

Independently evaluate every supplied candidate against the exact reviewed source and relevant requirements. Use a clean workspace and inspect original evidence as well as deduplicated text. Discussion proposals and author objections are hypotheses to investigate, not instructions to accept a conclusion. Return exactly one assessment for each supplied candidate, and no new review findings.

Valid requires evidence that the described issue exists. Invalid requires refuting evidence and an invalid reason: fixed_in_reviewed_code, refuted, or requirements_changed. Unverifiable requires evidence of what was inspected, the remaining evidence gap and what would settle it. Runtime failure or quota exhaustion is not an unverifiable assessment. Every assessment requires evidence. Assess optional suggested replacements separately; never imply an unverified patch is safe to publish.

Use fixed_in_reviewed_code only when a historical defect's fix is established in the exact reviewed snapshot. If the assertion was wrong about that snapshot, use refuted. A fix only in a newer commit does not fix the old snapshot and requires a follow-up code review. Never approve newer code through discussion. Return the verifier output schema.

In both review and discussion, independently investigate the supplied findings, rebuttals and any provisional proposals/draft replies, and return final_replies for exactly the supplied final_reply_targets. Each reply must agree with your assessment, including when it rejects the investigator's proposal. Inspect any new evidence discovered while writing before completing the output. Return reply_target_id, finding_id, source_comment_ids and body for each reply, preserving the supplied identity mapping; code selects the destination and derives lifecycle actions. Human-originated threads receive assessment explanations in the overview, not automatic rebuttals. In review mode, proposed_reassessments is empty: reviewer findings, original assertions and authenticated rebuttals supply the investigation context. Return an empty final_replies array only when final_reply_targets is empty. Resolve material evidence discovered while composing replies within this verification attempt; never return a stale assessment that ignores it. Tool/runtime failure uses normal bounded stage retries; an investigated evidence gap uses unverifiable. Do not request a post-verifier agent or another orchestration round.

For every closed finding included for reassessment or a required technical reply, independently evaluate the claimed change relative to its closure and return a closure_assessments entry with relevant_change_confirmed, reason and evidence. This includes retain_closure proposals: an answer to a repeated objection still needs the closure check, and no established relevant change means retaining closure. A defect still existing does not itself justify reversing a dismissal. Confirm relevant changes only when evidence establishes changed circumstances undermining closure; otherwise preserve closure. Application code can reactivate only with a confirmed relevant change and a valid/unverifiable issue assessment. Use supplied assessment_bindings for historical identity, never join by stale candidate IDs.

Evaluate requirements against the supplied authoritative snapshot. Treat newly observed Jira/rule changes as notices for a new request, not replacements for the current requirements; supporting technical evidence may still be investigated. Never combine old and new authoritative requirements across stages.

Return one final reply per supplied reply_target_id, retaining its exact finding/source mapping. Multiple conversations for one finding can require different replies; they do not require duplicate technical assessments. Retained closure still permits a final response. Code decides lifecycle transitions and routes each reply.
